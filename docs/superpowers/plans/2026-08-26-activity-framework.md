# Activity Framework Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the header's level and model pickers with an activity selector, and ship three dialogue activities — chat, focused chat, and story time.

**Architecture:** An activity is a property of a conversation, stored in a new nullable `activity` column and defaulting to `"chat"`. Activity definitions live in `prompt.js` as a data table that adds and suppresses system-prompt rules; chat and focused chat reuse the existing `turn()` loop unchanged, while story time drives that same loop repeatedly to generate a story one segment at a time.

**Tech Stack:** Plain ES2015+ in a single HTML file plus seven no-dependency modules. Node for tests, no framework. Supabase/PostgREST for sync. **No build step, no bundler, no `package.json`, no dependencies — do not add any.**

**Spec:** `docs/superpowers/specs/2026-08-26-activity-framework-design.md`

## Global Constraints

- **No dependencies anywhere, including tests.** No `package.json`, no bundler, no test framework.
- **Tests are plain node:** a `check(ok, label, detail)` counter, `process.exit(1)` at the end. Match the existing files exactly.
- **Run the suite with `sh test/run.sh`.** One suite: `node test/pace.test.js`.
- **`.githooks/pre-commit` runs the whole suite and refuses a failing commit.** If commits are rejected, run `git config core.hooksPath .githooks` — that is expected, not a problem to work around.
- **`VERSION` in `index.html` and `CACHE` in `sw.js` must move together** on every user-visible change. Current values: `v58 — 2026-08-26` and `hsk-chat-v58`. Task 10 owns the bump; do not bump in earlier tasks.
- **Any file the page loads must appear in `sw.js`'s `SHELL`.** This plan adds no new loaded files, so `SHELL` should not change. If you find yourself adding one, stop and re-read the spec.
- **Never hand-edit `data/hsk<N>.json`.** They are generated by `tools/convert.py`.
- **Module wrapper:** every extracted module ends with
  `if (typeof module !== "undefined" && module.exports) module.exports = api; else root.HSKX = api;`
- **Every module is loadable in node and in the browser.** No `window` references in the testable half.
- **App-authored Chinese in *samples* and *starters* must validate against its own level's allowlist.** Rule text is exempt — the existing rules already contain 英文, 语法 and 纠正, which are above HSK 1. Do not attempt to make rule text validate.
- **Commit after every task.** Use the message given in the task's final step.
- **`test/browser.test.js` speaks raw WebDriver over HTTP/JSON.** There is no
  Playwright and no `selenium-webdriver` — those would be dependencies. The
  helpers are `await exec(script, args)` (a script *string*; `return` a value,
  and read `args` as `arguments[0]`), `await waitFor(expr, label, timeoutMs)`,
  and the same `check(ok, label, detail)` counter. **Write ES5 inside `exec`** —
  `var`, `Array.prototype.map.call` — matching the existing blocks.
- **`S` is a `const` at `index.html:931`, so it is NOT on `window`.** Tests reach
  app state through the DOM and through the localStorage keys `saveChats()`
  writes: `hsk1chat.chats`, `hsk1chat.chatMsgs`, `hsk1chat.chatId`. Top-level

## Task 1: The activity contract in `prompt.js`

**Files:**
- Modify: `prompt.js` (add `ACTIVITIES`, extend `build()`)
- Test: `test/prompt.test.js`

**Interfaces:**
- Consumes: nothing.
- Produces:
  - `HSKPrompt.ACTIVITIES` — object keyed by activity id. Each value is
    `{ label: string, rules: string[]|null, reuse: null|"unused", gen: "turn"|"segments", converse: boolean }`
  - `HSKPrompt.activityFor(id)` → the definition, falling back to `ACTIVITIES.chat`
  - `build(opts)` gains `opts.activity` (string id, default `"chat"`) and `opts.storySegment`
    (`null`, or `{ index: number, of: number }`)

### Why `converse` exists

`build()` pushes three conversational turn-taking rules — answer the student, don't repeat them, correct then continue. Mid-story those are wrong: every segment would end by asking the learner a question. An activity must be able to *suppress* rules, not only add them.

## Task 2: `activity` through sync and schema

**Files:**
- Modify: `sync.js` (`conversationToRow`, `rowToConversation`, `mergeConversations`, `probeSchema`)
- Modify: `db/schema.sql`
- Test: `test/sync.test.js`

**Interfaces:**
- Consumes: nothing from Task 1.
- Produces: conversation objects carrying `activity: string` (always a non-empty string after a round trip; `"chat"` when the column is absent or NULL).

### The trap this task exists to avoid

`mergeConversations` rebuilds its merged object field by field. A field not added there is silently dropped on every sync — it survives locally and vanishes the moment a second device merges. It must also **not** be newest-wins like `title`: an activity is fixed at creation and never changes.

- Produces: `runStory()` → generates `STORY_SEGMENTS` assistant messages, then hands off to phase 2 (Task 9).

### Why segments, and why this size

`settlePace` converts a reply's Han characters into new-word credits at `DEFAULT_RATE = 45`, capped at `CREDIT_CAP = 3` with the remainder **discarded** (`pace.js:66`). A 600-character story as one turn earns three credits and throws the other ten away — so the activity most entitled to graded-reader density is the one place the cap silently removes it.

Segmenting restores it without touching a researched constant: each segment is one `turn()` call, so each earns its own credits and gets its own slate of three.

async function runStory() {

## Still required before this ships to users

**The two new activities are prompt changes, and CLAUDE.md requires a real-model A/B with counted outcomes before a prompt edit ships.** DEVELOPING.md records a "fix" that made a failure eight times likelier, which is why. `tools/prompt-ab.js` is the harness; extend it to build an activity's prompt rather than only the two list modes.

What to count, per activity:

- **Focused chat:** how many of the offered unused words the learner actually produces per session, against plain chat as the control. The activity's whole claim is that it moves words from taught to used, and out-of-level rate is not that measurement.
- **Story time:** out-of-level words per segment against a chat turn of the same length, and whether segments actually continue rather than restarting — the failure the position rule exists to prevent.

Note the in-app counters are keyed `S.stats[effectiveMode()]`. Measuring an activity's prompt separately means keying them by mode **and** activity; do that in the harness rather than shipping a second counter.

Seeds must stay namefree, and per `BACKLOG.md` should avoid inviting place names too until the validator handles them.
