# Tone ID Implementation Plan

> **For agentic workers:** advance ONE task per run. The `- [ ]` checkboxes in
> this file are the only cursor across runs — leaving them unticked makes the
> next run redo the work. Tick them in the same commit as the code.

**Goal:** Play a word, ask the learner which tone each of its syllables was,
cycling every installed Chinese voice. No model call, no network, no new table.

**Architecture:** One new pure module, `pinyin.js`, splits tone-marked pinyin
into syllables, reports each syllable's tone (0 = neutral) and applies sandhi.
`index.html` owns a new sheet — a fifth face in the activity menu — that plays
a word through a rotating voice and takes one answer per syllable.
`retrieval.js` gains `face` awareness in its day cap so tone rounds and
gap-fill stop sharing a daily slot. Credit rides the existing synced
`retrievals` table under `face: "toneid"`.

**Tech Stack:** Plain ES5-style browser JS, no build step, no bundler, no
dependencies — **anywhere, including tests**. Tests are plain
`node test/<name>.test.js` with a `check(ok, label, detail)` counter.

**Spec:** `docs/superpowers/specs/2026-11-03-tone-id-design.md` — read it before
Task 1. All five product decisions are settled there; do not reopen one.

## Global Constraints

- **No dependencies, no `package.json`, no build step.** Do not add any, in
  source or tests.
- **`pinyin.js` ends with exactly this wrapper**, like every extracted module:
  ```js
  if (typeof module !== "undefined" && module.exports) module.exports = api;
  else root.HSKPinyin = api;
  ```
  wrapped in `(function (root) { "use strict"; ... })(typeof globalThis !== "undefined" ? globalThis : this);`
- **`pinyin.js` is pure**: no DOM, no `S`, no network, no `Date.now()`, no
  `crypto`, no `Math.random()`. Anything time-, lexicon- or randomness-dependent
  is passed in.
- **A new file the page loads must be added in FOUR places** or the release test
  fails or the deploy 404s: `<script src>` in `index.html`, `SHELL` in `sw.js`,
  the `isShell` regex in `sw.js`, and `.github/publish-files`.
- **`VERSION` in `index.html` and `CACHE` in `sw.js` must move together**, and
  only on a task that changes something a user sees. A docs-or-tests-only task
  moves neither. **Version numbers: take the highest vNNN across main and every
  unmerged branch and add one. RE-COUNT EVERY TIME — do not trust the number
  written here.** As of 2026-11-03 main is v140 (v139 and v140 both merged that
  day) and two unmerged branches hold v141 and v142, so the next free number is
  **v143**. That figure was already stale once within hours of being written,
  which is the point: re-check before each bump: two branches carrying the same
  `CACHE` is not cosmetic — `sw.js`'s activate handler deletes every cache whose
  key differs from `CACHE`, so an identical name makes that sweep match nothing.
- **`PREFS_KEYS` in `sync.js` must never name `key` or `history`.** The new
  round-size setting goes in prefs; those two do not.
- **Constants live in the module and are never re-typed.** If a default changes,
  `RESEARCH.md` changes with it, with the citations from the spec.
- **Commit style:** Conventional Commits with a body explaining *why*. Run
  `sh test/run.sh` before every commit; `.githooks/pre-commit` runs it anyway
  and refuses a failing commit. The browser suite really runs on this machine.
- **Branch:** `build/tone-id`, already created off `main`. Never commit to
  `main`, never open a PR.
- **Every task adds a check that fails without its change.** Prove it: stash the
  change, run the suite, confirm the new check is the one that fails, restore.

### Task 1: `pinyin.js` — split unspaced pinyin into syllables and tones

Not demoable. Everything else rests on this, and it is the task most likely to
be underestimated: `wǒmen` is one string with one tone mark and two syllables.

**Files:**
- Create: `pinyin.js`
- Create: `test/pinyin.test.js`
- Modify: `test/run.sh` (add the new suite to the loop)

**Interfaces:**
- `HSKPinyin.split(p) -> string[] | null` — `null` when it cannot be split
  confidently. **Never guess**; a word that returns `null` is excluded from the
  pool by Task 2, which is how a wrong answer key is made impossible.
- `HSKPinyin.tones(p) -> number[] | null` — one entry per syllable, `0` for
  neutral (no mark).
- `HSKPinyin.SYLLABLES` — the legal-syllable set, exported so the test can
  assert against it rather than restating it.

**Approach:** longest-match split over the finite set of legal pinyin syllables,
after stripping tone marks for matching (`NFD`, drop the combining marks, match,
then map back to the marked substring). Handle the apostrophe convention if any
entry uses it. Mark each syllable's tone from the combining mark it carries, or
0 if it carries none.

- [x] **Step 1: Write the failing test.** Cover, at minimum: `wǒ` → `["wǒ"]`
      `[3]`; `wǒmen` → `["wǒ","men"]` `[3,0]`; `xiànzài` → `[4,4]`; `shénme` →
      `[2,0]`; `nǐhǎo` → `[3,3]` (citation — sandhi is Task 4, not here);
      a three-syllable word; and at least one string that must return `null`.
- [x] **Step 2: Implement `pinyin.js`** until the suite passes.
- [x] **Step 3: Run `split()` across EVERY entry in `data/hsk1.json` through
      `data/hsk6.json` and count what it returns `null` for.** WRITE THE RAW LIST TO
      A FILE and commit it as `tools/pinyin-unsplit.txt`; print only the count and
      about five examples. Do not dump the list into your own output. The 2026-11-05
      run died with "Output blocked by content filtering policy" while probing this
      exact data — long runs of combining tone marks and Han characters in a model's
      output can trip the filter, and an earlier version of this step told it to
      print the whole list. The file keeps the evidence where CLAUDE.md wants it
      ("print the raw thing and count") without putting it through the model.
      If the count is more than a few percent at HSK 1–3 the parser is wrong and the
      file says how — fix it rather than widening the exclusion. Record the final
      count in the commit body.
      **Result (2026-11-07):** 3 of 5,334 HSK 1–6 entries return null — two
      `a/b` alternative readings and the interjection `ng` — 1 at HSK 1–3. All
      5,331 splits have one syllable per Han character (or one fewer per erhua
      r); `test/pinyin.test.js` now asserts both over the whole list.

### Task 4: sandhi — teach it, and never punish a voice the app did not choose

**DEMOABLE.** The spec's decisions 3 and 6. 你好 is answered **2-3**.

- [ ] **Step 1: Enumerate from the data.** Find every word in HSK 1–6 whose
      sandhi form differs from its citation form, grouped by rule (3+3, 不, 一),
      and every word with **three** consecutive third tones. Write it straight to
      `tools/sandhi-words.txt` and commit it, the way the existing `*-results` files
      are kept; print only the per-rule counts. Same reason as Task 1 Step 3: a long
      dump of tone-marked pinyin through the model's own output is what killed the
      2026-11-05 run.
- [ ] **Step 2: Test** `sandhi([3,3]) -> [2,3]`, the 不 and 一 rules from the
      spec's table, and that a three-consecutive-third word is **excluded** from
      the pool rather than given a general rule.
- [ ] **Step 3: Implement `HSKPinyin.sandhi(tones)`** and widen the pool to the
      sandhi words.
- [ ] **Step 4: Accept BOTH forms.** Where the sandhi form differs from the
      citation form, both answers are correct. The reveal teaches the sandhi
      form and names the rule; a learner who hears a citation tone is not marked
      wrong. The evidence that voices apply sandhi is **iOS only** (Todd,
      2026-11-03, 你好 and 不是 through Notes), so this must degrade, never
      punish. Pin it with a test.

### Task 5: make the day cap face-aware

Not demoable, and required before Task 6 or tone taps corrupt gap-fill.

`credit()` keys its one-row-per-day cap on word + day, **ignoring `face`**, and
`countsFrom()` ignores `face` entirely. So a gap-fill credit on 我 would consume
the tone slot for 我 the same day, and a tone tap would raise the `n` that
*selects* gap-fill's words — breaking the spec's decision 5 in both directions.

Backward-compatible: every row already carries a face. `creditRetrieval`
defaults it (`index.html:6875`), both sync converters default it
(`sync.js:276`), and the column defaults it (`db/schema.sql:175`).

**Files:** `retrieval.js`, `test/retrieval.test.js`, `index.html`

- [ ] **Step 1: Test** that two rows for the same word and day with different
      faces both survive `credit()`, that two with the *same* face do not, and
      that `countsFrom(rows, "toneid")` ignores gapfill rows while
      `countsFrom(rows)` still pools everything.
- [ ] **Step 2: Implement.** Cap on word + day + face; `countsFrom(rows, face)`
      filters when given a face and pools when not, so `retrievalCounts()` keeps
      its present meaning until its caller is updated.
- [ ] **Step 3: Update `retrievalCounts()`'s callers** so gap-fill asks for its
      own face. Confirm no existing gap-fill test changes behaviour — if one
      does, the change is not backward-compatible and the step is wrong.
